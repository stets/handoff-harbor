A Bricks site is not handed off just because the WordPress login works.

The messy version: Bricks is licensed to the freelancer, templates are undocumented, global styles are easy to break, forms go to the wrong inbox, performance settings are fragile, backups are not scheduled, and the client thinks every post-launch adjustment is included.

This is not legal, tax, hosting, security, accessibility, or Bricks/WordPress policy advice. It is a practical closeout checklist for freelancers and small studios so ownership, licenses, template structure, launch acceptance, support boundaries, and paid maintenance options are written down before final payment gets weird.

What to document before a Bricks Builder project is accepted

WordPress, hosting, and license ownership

Confirm admin owner, hosting account, registrar/DNS, SSL, backups, update responsibility, Bricks license owner, child theme/custom code notes, and whether freelancer access stays or gets removed.

Bricks structure and editing rules

Record global styles, templates, headers/footers, theme styles, conditions, dynamic data, custom fields, reusable sections, and what the client can safely edit without breaking layout logic.

Forms, integrations, and performance stack

Test forms, SMTP, spam protection, analytics, pixels, Search Console, CRM/email integrations, caching, image optimization, security plugins, redirects, and cookie/privacy tools if used.

Training and support boundary

Explain safe content edits, risky Bricks/template/global-style changes, the included bug-fix window, excluded future work, and how change requests or care plans will be priced.

Copy/paste Bricks Builder website handoff checklist

  • ☐ WordPress admin owner, user roles, recovery email, 2FA, hosting login, domain registrar, DNS, SSL, and email provider are documented.
  • ☐ Bricks Builder license owner, license key location, renewal responsibility, theme/child-theme notes, custom CSS/JS/PHP, and plugin dependency list are recorded.
  • ☐ Global styles, breakpoints, theme styles, headers, footers, single/archive templates, conditions, popups, query loops, and reusable sections are summarized.
  • ☐ Dynamic data sources, custom post types, custom fields, taxonomies, menus, blog templates, and client-editable content areas are explained in plain English.
  • ☐ Forms, SMTP, notification recipients, autoresponders, CRM/newsletter integrations, spam protection, analytics, pixels, Search Console, and conversion events are tested.
  • ☐ Caching, minification, image optimization, CDN, security, backup, staging, update, and uptime-monitoring tools are listed with owner and risk notes.
  • ☐ Mobile/tablet/desktop checks, browser checks, 404/redirect checks, privacy/legal pages, alt text basics, and known accepted limitations are reviewed by the client.
  • ☐ Client editing notes explain safe text/image/blog edits, risky template/global-style/plugin/cache edits, and when to request paid help.
  • ☐ Included support window is stated, and new pages, template redesigns, SEO, copy, plugin changes, speed work, troubleshooting, or ongoing maintenance route to paid work.
